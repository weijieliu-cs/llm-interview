# 12 提示词与上下文工程

[返回首页](../README.md) · [题目索引](question-bank.md)

## 核心知识

提示词定义任务、约束、示例和输出要求；上下文工程进一步决定每轮装入哪些文档、工具结果、历史状态与记忆。二者的改进都应通过固定任务集验证。

建议以“任务说明 → 可信约束 → 可用数据 → 示例 → 输出约定”组织输入，明确哪些内容是外部证据。具体角色层级和模板由所用模型及服务协议决定。

## 常见面试题

<a id="c01"></a>
### C01｜Zero-shot、Few-shot 和指令微调如何区别？【P0】

**回答要点：** Zero-shot 只提供任务说明，Few-shot 在上下文中提供示例，二者不更新模型参数；指令微调通过数据和梯度改变参数。示例应覆盖典型模式与边界，避免答案泄漏和格式矛盾。可以先用 Few-shot 建立基线，再判断是否需要训练。

**追问：** 示例越多越好吗？会占用上下文并引入偏置，选择与当前任务相关、互补且格式一致的示例比机械增加数量更重要。

<a id="c02"></a>
### C02｜CoT 和 Self-consistency 如何使用及评估？【P1】

**回答要点：** CoT 提示通过中间推理示范或任务分解帮助完成多步问题；Self-consistency 采样多条路径并聚合最终答案。改进依赖任务和模型，不能把可见推理文本当作正确性的证明。比较时同时报告正确率、采样数、输出 token 和延迟。见 [CoT](https://arxiv.org/abs/2201.11903) 与 [Self-consistency](https://arxiv.org/abs/2203.11171)。

**追问：** 多数答案都错时怎么办？独立验证器、工具计算或证据检查可能更有效，增加相关性很强的错误样本无法保证投票正确。

<a id="c03"></a>
### C03｜长对话的上下文预算如何管理？【P0】

**回答要点：** 为任务约束、当前问题、关键证据和预期输出预留预算，采用近期窗口、结构化状态、可追溯摘要与按需检索。区分短期会话状态和长期记忆，明确用户身份、生命周期和删除机制。摘要会丢信息，应保留出处并在需要时取回原始记录。

**追问：** 自动截断最早消息有什么风险？可能丢失约束、实体定义和未完成事项，工具调用及结果还可能被截成不完整对。

<a id="c04"></a>
### C04｜Function Calling、MCP 和 Agent 是什么关系？【P1】

**回答要点：** Function Calling 通常让模型生成符合工具描述的调用意图及参数，由应用执行；MCP 定义客户端与服务器之间交换工具、资源等能力的协议；Agent 在此之上管理状态、选择动作和终止。它们处于不同层次，协议接入不会自动提供正确规划、权限或任务成功保证。见 [MCP 官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)。

**追问：** 工具参数符合 schema 就能执行吗？还需校验资源归属、业务前置条件、幂等性和用户授权；模型输出本身不是授权凭据。

<a id="c05"></a>
### C05｜如何选择 LangChain 等框架或直接编排？【P1】

**回答要点：** 围绕集成成本、状态管理、流式输出、错误重试、可观测性、版本维护与可测试性比较。先定义清晰的模型、检索和工具接口，避免业务规则依赖隐式默认值。框架帮助组织组件，最终应能解释实际的数据流、调用次数和失败路径。

**追问：** 框架升级后效果变差如何排查？固定依赖版本，记录渲染后的提示词、检索结果、实际请求和输出，进行版本对照。应用组织方式可参考 [Datawhale llm-universe](https://github.com/datawhalechina/llm-universe)。

<a id="c06"></a>
### C06｜如何持续维护提示词而不在测试集上过拟合？【P0】

**回答要点：** 将提示词视为版本化配置，记录修改目的、开发集结果与失败类型。在开发集迭代，独立测试集仅用于阶段性验收，按任务子集和长尾样本检查回归。上线观察完成率、拒答、工具错误和成本，保留回滚能力。

**追问：** 一个示例从错误变正确能否说明提升？不能。单例可能是偶然或针对性适配，需要在固定分布和边界集上证明收益。

## 易错点

- 把成功演示一次当作稳定工作流。
- 自动摘要后删除全部原始证据，无法验证错误来源。
- 把工具协议、应用框架和模型决策能力混为一谈。
